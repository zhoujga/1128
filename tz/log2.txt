SMS OGR Driver GDAL 3.13 API 兼容性修复日志
==========================================
日期: 2026-03-26

## 问题概述
修复 SMS (Standard Mapping Service) OGR driver for GDAL 3.13 API 兼容性。主要问题是 A (polygon) 层读取特征有几何数据但数量为0。

## 发现的问题

### 1. ZB文件跳过Bug (已修复)
发现在 ReadFeatures() 函数中，跳过 P section header 时只读取了 SX 但没有读取 ZB，导致文件位置不对齐。

修复: 在 line 306 添加了 std::getline(*m_pInZB, lineZB);

### 2. A Section额外读取Bug (已修复)
发现在 PLA == 2 分支中，line 492 有一个额外的 std::getline(*m_pInZB, lineZB); 在循环之前读取了一行，导致特征计数错误。

修复: 删除 line 492 的额外读取。

### 3. Windows行尾格式 (CRLF) 问题
CZB文件使用 Windows 行尾格式 (CRLF, \r\n)。在多环多边形解析时，marker 检测因为 \r 字符而失败。

修复: 在 marker 检测中添加了 \r 的处理：
```cpp
size_t nonSpace = remaining.find_first_not_of(" \t\r\n");
```

### 4. 多环多边形解析逻辑问题

#### CZB文件格式分析
A section 的多环多边形格式:
```
Line 13017: polyID=1108, polyX=17402.17, polyY=5329.39, ringCount=2, coordCount=9
Line 13018-13019: 8个坐标对 (6 + 2，跨越两行)
Line 13020: marker=5 (standalone line - exterior ring has 5 coordinates)
Line 13021: 4个坐标对 (interior ring, 9-5=4)
```

关键发现:
- Marker 出现在坐标数据之后，而不是之前
- Marker 行格式: "         5" (前面有空格)
- 需要先读取所有坐标，然后在 marker 处截断

#### 多环多边形数据
CZB文件中 ringCount > 1 的多边形:
- 1108: ringCount=2, coordCount=9
- 1173: ringCount=2, coordCount=10
- 1220: ringCount=2, coordCount=8
- 1380: ringCount=2, coordCount=8
- 1391: ringCount=2, coordCount=27
- 1396: ringCount=2, coordCount=21 (最后一行有 marker=10)

### 5. 当前解析逻辑

读取坐标时:
1. 读取 header 行获取 nPolyID, dPolyX, dPolyY, nRingCount, nCoordCount
2. 循环读取坐标行，直到 coordsRead >= nCoordCount
3. 在读取过程中检测 marker 行 (单行只有一个整数)
4. 发现 marker 时，记录 firstRingSize = coordsRead (读取到 marker 时的坐标数)
5. 跳过 marker 行继续读取
6. 最后根据 firstRingSize 和 nCoordCount 构建 ringCounts

问题分析:
- 对于 poly 1108: nCoordCount=9, marker=5
- 读取逻辑: 6 coords + marker(跳过) + 4 coords = 10 coords in file
- 但 marker 检测后 firstRingSize = 8 (因为 marker 前读取了8个坐标)
- resize 后应该是 9 coords: [0-4] exterior, [5-8] interior
- 但实际输出没有多环多边形

### 6. SMID编号问题
当前输出 SMID 从 1398 开始而不是从 1 开始。
这是因为 m_nGlobalFIDCounter 是全局计数器，会累计所有层的特征数。

当前输出统计:

## 多环多边形解析问题分析 (2026-03-26)

### 问题根因
通过 Python 模拟解析发现：
- poly 1108 的 marker=5 在所有坐标读取完毕后才被检测到
- 原因：marker 行位于坐标之间，但检测逻辑在读取坐标之后才检查

### 文件结构
```
Line 13017: polyID=1108, ringCount=2, coordCount=9
Line 13018: 6个坐标对
Line 13019: 3个坐标对 (coordsRead=9, 已达到nCoordCount)
Line 13020: marker=5 (此时才检测到marker, firstRingSize=9)
Line 13021: 4个坐标对 (但coordsRead已达到nCoordCount，不会再读取)
```

### 当前逻辑问题
1. marker 检测在循环末尾检查，而不是在读取行时检查
2. coordsRead >= nCoordCount 时跳出循环，marker 行被错过
3. 即使检测到 marker=5，firstRingSize=9（所有坐标已读完）

### 正确理解
marker=5 表示 exterior ring 有 5 个点
- exterior: 前 5 个点
- interior: 后 4 个点

但因为 marker 出现在坐标数据之后，当前逻辑无法正确分割。

### 需要修改的逻辑
1. 先读取所有行（包括 marker）
2. 找到 marker 的位置（coordsRead 在 marker 行之前的值）
3. 根据 marker 值分割坐标

### 备选方案
如果 marker 格式不可靠，可以尝试：
1. 检测坐标序列中的重复点（环的闭合点）
2. 使用 nCoordCount 和 nRingCount 估算每环的点数
